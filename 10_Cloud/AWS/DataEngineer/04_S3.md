# Amazon S3 (Simple Storage Service)

S3 es el servicio más importante del examen DEA-C01. Es la columna vertebral de casi toda arquitectura de datos en AWS: es el data lake por defecto, el
staging para Redshift, el origen/destino de Glue, EMR, Athena, Firehose y prácticamente todo. Te lo cubro a fondo.

### Conceptos fundamentales

S3 es object storage (almacenamiento de objetos), no block storage (EBS) ni file storage (EFS). Esto importa:
- Guardas objects (archivos + metadata) dentro de buckets.
- Cada object se identifica por su key (la "ruta" completa, ej. datos/año=2025/archivo.parquet).
- No hay carpetas reales — los "folders" son solo prefixes (prefijos) en el key. El / es convención visual.
- Capacidad virtualmente ilimitada; cada object de 0 bytes hasta 5 TB.
- Es un servicio regional, pero los bucket names son globalmente únicos.
- **Durability**: 99.999999999% (11 nueves) — diseñado para no perder objetos. Los datos se replican automáticamente en múltiples Availability Zones (AZs)
dentro de la región.
- **Availability**: varía según la storage class (99.5% a 99.99%).

Esto es consecuencia de que S3 copia tus datos en ≥3 AZs (excepto One Zone-IA).

### Storage Classes

| Storage Class                      | Caso de uso                                    | Clave                                                                                           |
| ---------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| S3 Standard                        | Datos de acceso frecuente                      | Mayor costo de storage, sin costo de retrieval                                                  |
| S3 Intelligent-Tiering             | Patrón de acceso desconocido o cambiante       | Mueve objetos entre tiers automáticamente; sin retrieval fees. Respuesta típica cuando "no se conoce el patrón de acceso" |
| S3 Standard-IA (Infrequent Access) | Acceso poco frecuente pero rápido cuando se necesita | Menor costo de storage, pero cobra retrieval fee                                          |
| S3 One Zone-IA                     | IA pero datos recreables                       | Una sola AZ → más barato pero menos resiliente                                                  |
| S3 Express One Zone                | Para alro rendimiento en consultas             | latencia "single-digit ms". Soporta altos requests/second                                       |
| S3 Glacier Instant Retrieval       | Archive con acceso inmediato ocasional         | Milisegundos                                                                                    |
| S3 Glacier Flexible Retrieval      | Archive, retrieval en minutos-horas            | Antes "Glacier"                                                                                 |
| S3 Glacier Deep Archive            | Archive de largo plazo (7-10 años)             | El más barato; retrieval en horas                                                               |


### Lifecycle Policies

Permiten automatizar transiciones entre storage classes y expiración de objetos. Ejemplo:

Día 0:   S3 Standard
Día 30:  → Standard-IA
Día 90:  → Glacier Flexible Retrieval
Día 365: → Glacier Deep Archive
Día 2555 (7 años): Expire (delete)

Puntos clave:
- Puedes filtrar por prefix o tags.
- Gestiona current versions y noncurrent versions por separado (importante con versioning activo).
- Sirve para optimización de costos (dominio de Operations/Cost).

### Partitioning

Cómo organizas los keys afecta directamente el costo y performance de Athena, Glue, EMR y Redshift Spectrum.

Hive-style partitioning (el estándar): `s3://mi-datalake/eventos/year=2025/month=10/day=19/datos.parquet`

Por qué importa:
- **Athena/Spectrum** hacen partition pruning: solo leen las particiones necesarias → menos datos escaneados = menos costo (Athena cobra por TB escaneado).
- **Glue Crawlers y MSCK REPAIR TABLE / partition projection** registran estas particiones.

> "reducir costo de queries en Athena" → particionar + usar formato columnar (Parquet) + comprimir.

### Formatos de archivo

Aunque no son S3 per se, se guardan en S3 y son clave:
- **Parquet / ORC** → columnar, comprimidos, ideales para analytics. Respuesta por defecto para optimizar queries y costos.
- **Avro** → row-based, bueno para streaming/esquemas que evolucionan.
- **JSON / CSV** → row-based, legibles pero ineficientes para analytics.

> "optimizar performance/costo de queries analíticas" → convertir a Parquet (Glue puede hacerlo).

### S3 Performance

- Escala automáticamente: 3,500 PUT/COPY/POST/DELETE y 5,500 GET/HEAD requests por segundo por prefix.
- Para más throughput → usar múltiples prefixes en paralelo.
- Multipart Upload: recomendado para objetos >100 MB (obligatorio para >5 GB). Sube partes en paralelo; más rápido y resiliente.
- S3 Transfer Acceleration: usa edge locations de CloudFront para subidas rápidas desde lejos.
- Byte-Range Fetches: descargar partes específicas de un objeto en paralelo.

### Seguridad

#### Encryption at rest:
- **SSE-S3** (AES256): AWS gestiona las keys. Simple. Default actual.
- **SSE-KMS**: usa AWS KMS; permite audit trail (CloudTrail), rotación y control de acceso a la key. ⚠️ Ojo: puede generar throttling de KMS en cargas de alto volumen (límite de requests a KMS). Mitigación: S3 Bucket Keys (reduce llamadas a KMS).
- **SSE-C**: el cliente provee la key; AWS no la almacena.
- **Client-Side Encryption**: cifras antes de subir.

#### Encryption in transit:

- **HTTPS/TLS**. Puedes forzarlo con una bucket policy (aws:SecureTransport).

### Control de acceso:

- **IAM policies** (sobre la identidad).
- **Bucket policies** (resource-based, sobre el bucket). Para cross-account access y condiciones.
- **ACLs**: legacy, AWS recomienda deshabilitarlas (Object Ownership → Bucket owner enforced).
- **Block Public Access**: setting a nivel cuenta/bucket que bloquea acceso público. Respuesta típica a "evitar exposición accidental de datos".
- **S3 Access Points**: endpoints con policies dedicadas para simplificar acceso a datasets compartidos a gran escala.
- **VPC Gateway Endpoint for S3**: acceso privado a S3 sin pasar por internet. Clave para seguridad y para que recursos en VPC (EMR, Redshift) lleguen a S3 privadamente.

####  S3 Access Points

Problema: Imagina un data lake en un solo bucket, compartido por decenas de aplicaciones, equipos y usuarios, cada uno con necesidades de acceso distintas. Si gestionas todo con una sola bucket policy, esa policy crece hasta volverse un documento gigantesco, difícil de leer, auditar y mantener. Además, las bucket policies tienen un límite de tamaño (20 KB), así que a cierta escala simplemente no cabe todo.

Un S3 Access Point es un endpoint de red con nombre propio que se adjunta a un bucket, y que tiene su propia **access policy** dedicada. En vez de una bucket policy monolítica, creas múltiples access points, cada uno con permisos acotados para un caso de uso específico.

```
                      ┌── Access Point "finanzas"   → policy: solo prefix /finanzas, solo lectura
  Bucket              ├── Access Point "ml-team"    → policy: prefix /datasets, lectura/escritura
  "data-lake"  ◄──────┤── Access Point "externo"    → policy: solo un prefix, solo desde una VPC
                      └── Access Point "logs"       → policy: solo escritura de logs
```
Características clave:

- Cada access point tiene su propia policy (similar a una bucket policy, pero acotada a ese punto de acceso). Divide y simplifica la gestión de permisos.
- Tiene un nombre único (dentro de la cuenta + región) y su propio DNS endpoint/ARN.
- Network origin control: puedes configurar un access point como:
    - Internet (accesible desde internet), o
    - VPC (solo accesible desde una VPC específica) → refuerza que el tráfico sea privado. Muy útil para seguridad.
- El acceso final siempre respeta tanto la policy del access point como la del bucket (ambas se evalúan; la del bucket sigue siendo el límite superior).
- El código cambia un poco al llamar el bucket, pues ya no referencia el nombre del bucket directamente sino que se le pasa el arn del access point (o el alias)

#### S3 Object Lambda Access Points

Hay un tipo especial: S3 Object Lambda Access Point. Permite transformar los datos "al vuelo" cuando se recuperan, pasando el object por una función Lambda antes de devolverlo. Casos:

- Redactar/enmascarar PII (data masking) según quién consulta.
- Convertir formatos, filtrar filas/columnas, redimensionar, etc.
- Devolver vistas distintas del mismo dato a distintos consumidores.

### Versioning

- Mantiene múltiples versiones de un object → protege contra borrados/sobreescrituras accidentales.
- Una vez activado, solo se puede suspender, no desactivar del todo.
- Un delete crea un delete marker (no borra realmente).
- Se combina con lifecycle para gestionar noncurrent versions.

### S3 Object Lock

- WORM (Write Once Read Many): impide borrar/modificar objetos.
- Modos: 
    - **Governance** (usuarios con permiso especial pueden saltarlo) 
    - **Compliance** (nadie, ni root, puede borrarlo hasta que expire).
- Requiere versioning. Respuesta típica a "requisitos regulatorios / retención inmutable".

### Replication

- CRR (Cross-Region Replication): replica a otra región → DR(disaster recovery), latencia, compliance.
- SRR (Same-Region Replication): agregar logs, replicar entre cuentas en la misma región.
- Requiere versioning activado en origen y destino.
- Es asíncrona.

### Event Notifications e integración

S3 puede disparar eventos cuando ocurre algo (ej. s3:ObjectCreated:*):
- Destinos: Lambda, SNS, SQS, y EventBridge.
- Caso típico: llega un archivo nuevo → dispara una Lambda o un Glue job / Step Functions para procesarlo. Patrón central de event-driven data pipelines.

> EventBridge da filtrado más avanzado y más destinos.

### S3 Select / Glacier Select

Permite usar SQL para recuperar solo un subconjunto de datos de un object (CSV/JSON/Parquet) → menos datos transferidos. 

> Útil cuando no quieres montar Athena para algo simple.

### S3 Storage Lens & Analytics

- Storage Lens: visibilidad y métricas de uso/actividad a nivel organización → optimización de costos.
- Storage Class Analysis: recomienda cuándo mover datos a IA.

### S3 Server Access Logs

registra requests detallados hechos a un bucket. Cada vez que alguien hace un GET, PUT, DELETE, etc. sobre el bucket, se genera un log con información como: Quién hizo el request, La operación (REST.GET.OBJECT, etc.), El key del object afectado, Timestamp, IP de origen, Código de respuesta HTTP y errores, Bytes transferidos, tiempo de la operación, etc.

Sirve para auditoría de seguridad, análisis de accesos, troubleshooting y entender patrones de uso.

- Necesitas un bucket de destino (target bucket) separado donde se depositan los logs.
- El target bucket debe estar en la misma región que el source bucket.
- Los logs se entregan mediante el grupo S3 Log Delivery.
- Los logs se escriben como objetos en el target bucket, agrupados periódicamente.
- La entrega de logs es **best-effort** → puede haber retrasos (minutos a horas) y, en raras ocasiones, algún log podría no entregarse o duplicarse.
- No es adecuado cuando necesitas un registro completo, garantizado y en tiempo casi real para compliance estricto.
- No tiene costo adicional por la feature en sí (solo pagas el storage de los logs).

### S3 Presigned URL

Una presigned URL es una URL temporal que da acceso a un object específico de S3 sin que el usuario necesite credenciales de AWS ni permisos propios.

- La genera alguien que sí tiene permisos (usuario o role) y "firma" la URL con sus credenciales.
- Quien recibe la URL hereda esos permisos, pero solo para esa acción (GET para descargar o PUT para subir) y ese object.
- Expira tras un tiempo definido (DurationSeconds).

Caso de uso típico: dar a un usuario externo la descarga/subida de un archivo privado sin hacer público el bucket.

### S3 CORS (Cross-Origin Resource Sharing)

mecanismo que permite que una aplicación web alojada en un dominio (origin) haga requests a un bucket de S3 que está en otro dominio distinto. Por defecto los navegadores bloquean estas peticiones cross-origin; CORS las habilita de forma controlada.

Cómo se configura: con una CORS configuration en el bucket (documento JSON, antes XML) donde defines:
- AllowedOrigins — qué dominios pueden pedir (ej. https://miapp.com)
- AllowedMethods — qué métodos HTTP (GET, PUT, POST, etc.)
- AllowedHeaders / ExposeHeaders
- MaxAgeSeconds — cuánto cachea el navegador la respuesta preflight

Caso de uso típico: un frontend (JavaScript en el navegador) que sube/descarga objetos directamente a/desde S3 desde un dominio diferente.

> Punto clave: lo aplica y exige el navegador, no es un control de seguridad del lado de S3 (no reemplaza IAM/bucket policies).


## Aclaraciones

### Bucket Policy vs Trust Policy

Las dos son resource-based policies. Por eso ambas llevan el campo Principal. Pero se adjuntan a recursos distintos y responden a preguntas distintas:

|                            | Bucket Policy                                       | Trust Policy                                          |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| ¿A qué recurso se adjunta? | A un bucket de S3                                   | A un IAM Role                                         |
| ¿Qué pregunta responde?    | "¿Quién puede hacer qué sobre este bucket/objetos?" | "¿Quién puede asumir este role?"                      |
| Acciones típicas (Action)  | s3:GetObject, s3:PutObject, s3:ListBucket...        | Siempre sts:AssumeRole (o variantes WebIdentity/SAML) |
| ¿Para qué sirve?           | Controlar acceso a datos del bucket                 | Controlar quién puede ponerse el "sombrero" del role  |


Piensa en un IAM Role como un "sombrero" que una identidad se pone temporalmente:

- La trust policy es el guardia en la puerta que dice: "¿Tú tienes permiso para ponerte este sombrero?" — controla quién puede asumir el role. Su acción siempre es sts:AssumeRole.
- La permissions policy del role (otra cosa distinta) dice: "Una vez que llevas el sombrero puesto, ¿qué puedes hacer?" — ej. leer S3, escribir en Redshift.
- La bucket policy no tiene nada que ver con "ponerse sombreros". Vive en el bucket y dice: "estas identidades pueden leer/escribir estos objetos."

Trust policy (adjunta al role):
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
        "Effect": "Allow",
        "Principal": {
            "Service": "glue.amazonaws.com"    // Puede ser un servicio o una cuenta
        },
        "Action": "sts:AssumeRole"            // ← la acción SIEMPRE es asumir
        }
    ]
}
```

Bucket policy (adjunta al bucket):
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
        "Effect": "Allow",
        "Principal": { "AWS": "arn:aws:iam::111111111111:role/GlueServiceRole" },
        "Action": "s3:GetObject",                  // ← acción sobre datos
        "Resource": "arn:aws:s3:::mi-datalake/*"   // ← SOBRE QUÉ recurso
        }
    ]
}
```

Diferencias visibles:
- La trust policy no tiene Resource (el recurso es el role al que está adjunta).
- La trust policy siempre usa `sts:AssumeRole`; la bucket policy usa acciones `s3:*`.


### Cross-Account Access a S3

| Criterio               | Patrón A: Resource-based                | Patrón B: AssumeRole                      |
| ---------------------- | --------------------------------------- | ----------------------------------------- |
| ¿Interviene STS?       | No                                      | Sí (sts:AssumeRole)                       |
| Credenciales que usa   | Propias (Cuenta B)                      | Temporales (Cuenta A)                     |
| Dónde vive el role     | Cuenta B                                | Cuenta A                                  |
| Qué habilita el acceso | Bucket policy (A) + identity policy (B) | Trust policy (A) + permiso AssumeRole (B) |
| Tipo de credencial     | Permanente                              | Temporal (expira)                         |
| Alcance                | Solo S3 (puntual)                       | Múltiples servicios (general)             |


Cuándo elegir cada uno

- Patrón A → acceso simple y puntual a un bucket de S3.
- Patrón B → acceso a varios servicios de la otra cuenta (S3 + Glue Data Catalog + Redshift, etc.), cuando quieres credenciales temporales, o centralizar acceso. Servicios sin resource-based policy completa (ej. DynamoDB) obligan a este patrón.

### bucket-level operations vs object-level operations

An example for bucket-level operations: 

    `"Resource": "arn:aws:s3:::bucket_name"`

Examples for object-level operations:

    `"Resource": "arn:aws:s3:::bucket_name/*"` for all objects in the bucket.
    `"Resource": "arn:aws:s3:::bucket_name/prefix/*"` for objects under a certain prefix in the bucket.

Esta es la razón por la que en los permisos se deben dar ambos
```json
{
    "Sid": "DenyInsecureTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
        "arn:aws:s3:::mi-datalake",
        "arn:aws:s3:::mi-datalake/*"
    ],
    "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
    }
}
```
